## Why it is four plans and not one

The request is one feature, but it crosses a backend gap (there is no create
API at all), a new UI surface, an existing UI surface, and a validation pass.
Each has a different risk profile and a different verification story — 001 and
004 are unit-testable Python, 002 and 003 are manual-check JS in a repo with no
frontend test runner. Splitting them keeps each plan's done criteria honest.

## Key facts established during recon

Inlined here so a reader does not have to re-derive them:

- **Claude Code removed its own interactive agent wizard in v2.1.198.** `/agents`
  now prints a note telling you to ask Claude or edit `.claude/agents/`
  directly. Source: <https://code.claude.com/docs/en/sub-agents>, fetched
  2026-08-06. There is no guided authoring path for agents anywhere, which is
  what makes 002 worth building.
- **`skills:` is a real frontmatter field** and is the right answer to "reference
  specific skills from an agent". It preloads each listed skill's *full content*
  into the agent at startup. It is not an access control — an agent can still
  invoke unlisted skills through the `Skill` tool.
- **A skill with `disable-model-invocation: true` cannot be preloaded**, and a
  listed skill that is missing or disabled is skipped with a debug-log warning
  and no visible error. This is why 001 adds `no_model_invoke` to the scan and
  004 warns about unresolvable entries.
- Agent frontmatter has **no published JSON Schema**, unlike `settings.json`
  (which this repo vendors and syncs via `tools/sync_settings_schema.py`). So
  the field vocabularies in 002 and 004 are hand-maintained snapshots with an
  explicit drift note, not generated.
- The repo has no linter, formatter, typechecker, bundler or frontend test
  runner, by design (Python stdlib only, no build step). The only gates are
  `python3 -m unittest discover tests`, `python3 -m compileall`, and
  `node --check`. No plan may add a toolchain.

## Considered and rejected

- **A multi-step wizard with a stepper component.** The repo has no wizard
  primitive and adding one to `ui.js` for a single caller would be the largest
  change in the set. A single scrolling form with the reference beside it shows
  every field at once, which suits the task better than hiding two-thirds of it
  behind Next buttons.
- **Generating the agent YAML in Python.** It would be unit-testable, which is
  a real loss. But the builder shows a live preview of the file, and two
  generators — one for the preview, one for the write — is exactly how a preview
  starts lying. Plan 002 keeps generation in one place in the browser and tests
  it with a `node -e` output check instead.
- **Fetching the agent docs at runtime.** The app is offline-first by design
  (the settings schema is vendored for this reason) and the reference is most
  needed at the moment you cannot go and look it up. The docs ship inlined.
- **A "New" button on all four item tabs.** The backend from 001 is generic, but
  the guided form is agent-shaped. A half-guided form for skills, commands and
  output styles would be worse than the terminal. If those get creation, each
  wants its own template and its own field set.
- **Validating `mcpServers:` entries against configured servers.** The field
  also accepts inline server definitions, so "not a configured server" is not an
  error and the check would be noise.
